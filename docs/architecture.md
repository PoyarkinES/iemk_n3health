# Архитектура

## Общая схема

```text
EmkConfig (ручной запуск) ──> Forms ──> Application Use Cases
EmkWinService ──> ServiceRunner ─────> Application Use Cases
                                         │
                                         ├─> Application Ports
                                         │    └─> Infrastructure
                                         │         ├─> ODBC ──> база МИС
                                         │         ├─> WCF ──> PIX / EMK
                                         │         └─> документы, настройки и журналирование
                                         └─> Domain

Emk (legacy) ──> EmkSendingService ──> старые репозитории и WCF-клиенты

EmkCda ── модели и генерация CDA
EmkTests ── модульная проверка бизнес-сценариев без внешней инфраструктуры
```

## Поток отправки через Clean Architecture

1. `EmkConfig.Program` и `EmkWinService.Program` создают DI-контейнер и регистрируют `Emk.Application` и `Emk.Infrastructure`.
2. `EmkConfig.Forms.EmkMainForm` вызывает `ISendPatientDataUseCase` или `IUpdatePatientDataUseCase`; формы не обращаются к ODBC/WCF напрямую.
3. `EmkWinService.EmkWinSvc` запускает `ServiceRunner`, который читает активные настройки и периодически вызывает `ISendPatientDataUseCase`.
4. Use Cases загружают данные и проверяют правила через Application Ports.
5. Реализации Infrastructure используют ODBC и WCF-адаптеры, а результаты и ошибки записываются через `ILoggerService`.

Для периодического режима даты берутся из параметров `SendingType`, `DateInterval`, `IntervalFrom` и `IntervalTo`. Служба проверяет новые данные раз в пять минут.

Если пациент не дал согласие на передачу персональных данных, отправка разрешается только при заданных `UnknownPatientFirstName` и `UnknownPatientGivenName` в `appSettings`. В запрос PIX передаются только эти фамилия и имя; остальные персональные данные не включаются. При пустом или неполном наборе настроек действует обычный запрет отправки без согласия. Настройки конфигурационной программы и службы находятся в разных `.config` файлах; для службы значения следует задать в `EmkWinService.exe.config` отдельно.

Проверки и независимые чтения данных местами выполняются параллельно. Состояние пациента и случая должно оставаться локальным для конкретного запроса, а не храниться в полях долгоживущих сервисов.

## Слои и границы компонентов

- **Domain** (`Emk.Domain`) — сущности, перечисления, value objects и доменные исключения.
- **Application** (`Emk.Application`) — use cases, DTO и порты; не зависит от ODBC, WCF или UI.
- **Infrastructure** (`Emk.Infrastructure`) — адаптеры портов: ODBC-репозитории, WCF-клиенты, файловые настройки и логирование.
- **Presentation** (`EmkConfig`, `EmkWinService`) — композиция DI и UI/служба, вызывающие Application use cases.
- **`Emk`** — прежняя реализация, сохранённая для обратной совместимости; новые точки входа не используют `EmkSendingService` для отправки.
- **`EmkSendingDependencies.cs`** — контракты внешних зависимостей и адаптеры к репозиториям/WCF-клиентам; точки внедрения заглушек в тестах.
- **`Emk/Repository`** — SQL-запросы, ODBC-доступ и преобразование строк БД в модели.
- **`Emk/Services/PixService.cs` и `EmkService.cs`** — старые преобразования моделей интеграции и вызовы соответствующих WCF-сервисов.
- **`Emk/Services/Docs`** — подготовка документов EMK и вложений; `DocSelector` выбирает класс по `InternalDocType`.
- **`DoctorFileService`** — чтение и сохранение `SmoSettings.xml`, включая список врачей и настройки по умолчанию.
- **`EmkCda`** — отдельные CDA-модели и генератор; не путать с преобразованием документов EMK.

## Конфигурация и окружение

- Приложения используют общую ODBC-конфигурацию `EmkService/EmkDb.config`, подключённую через `configSource`; при развёртывании проверьте, что файл попал рядом с конфигурацией приложения.
- Точки входа получают строку подключения по имени `EmkDb` через `ConfigurationManager`; не помещайте реальные параметры подключения в репозиторий.
- Строка подключения должна соответствовать установленному драйверу и DSN. Успешная компиляция не подтверждает доступ к базе.
- Адреса сервисов и учётные идентификаторы зависят от стенда. Не используйте демонстрационные или локальные значения как производственную конфигурацию.
- `SmoSettings.xml` читается относительно расположения сборки `Emk`; проверьте наличие файла в каталоге приложения при установке службы и ручного приложения.
- Настройки и логи могут содержать персональные данные. Ограничивайте доступ, сроки хранения и распространение этих файлов.

## Известные незавершённые области

- `EmkSendingServiceExt` содержит незаполненные операции создания/закрытия случая, добавления шага и медицинской записи.
- `DocAppointedMedication` и `DocControlCardDispensaryObservation` выбираются селектором, но создание документов пока не реализовано.
- Сквозную совместимость ODBC-запросов и WCF-контрактов следует подтверждать на тестовом стенде: в обычном unit-test запуске этих систем нет.

Для списка актуальных инженерных рисков и дальнейших улучшений смотрите историю аудита и задачи проекта; этот документ описывает границы системы, а не заменяет бизнес-спецификации.
